# 自定义菜品选择设计规格

## 1. 设计结论

用户可以在设置页从应用内置的固定菜品库中选择一组菜品，保存为当前设备上的“自定义菜品”。自定义列表允许混合大类和小类，至少包含 3 个菜品。

组队模式中，房主创建房间时读取本地自定义列表，并将它作为房间级快照提交给后端。房间创建后，自定义列表被冻结；房主、客人和设置页的后续变化都不影响当前房间。客人加入房间时获取同一份快照，开始游戏时直接使用房间快照，不再重复发送菜品 ID。

自定义菜品不是新的全局菜单版本，也不是用户可编辑的菜品库。它只是当前固定菜单中的一个房间选择子集。

## 2. 范围

### 包含

- 设置页编辑当前设备的自定义菜品。
- 从大类和小类中混合选择。
- 至少 3 个菜品才能保存。
- 创建房间时提交一次自定义菜品快照。
- 客人加入房间时获取房主快照。
- 房间状态更新只同步快照 Hash 和数量，不重复传输完整 ID 列表。
- 轮次开始时复制房间快照，保证选择和结果可恢复。
- 菜单版本和 Hash 校验。

### 不包含

- 用户新增菜品、编辑菜品名称或上传图片。
- 跨设备同步自定义列表。
- 房间创建后修改自定义列表。
- 客人使用自己的自定义列表参加房主房间。
- 自定义菜品之间的父子分类关系。

## 3. 设置页交互

设置页从首页进入，包含：

- 顶部返回按钮。
- “自定义菜品”标题。
- 已选数量，例如“已选 12/53”。
- “全部 / 大类 / 小类”筛选，仅改变展示范围，不改变混合选择规则。
- 带图片、名称和数据集标签的复选列表。
- 底部固定“保存”按钮。

编辑使用独立草稿状态。只有草稿数量不少于 3 个时“保存”按钮可用；保存操作原子替换本地已保存配置。用户有未保存修改时返回，必须通过确认框确认离开。

本地数据使用 `localStorage` 保存，建议键名为 `lets-eat.custom-foods.v1`：

```json
{
  "catalogVersion": "v2",
  "itemIds": ["cantonese", "hotpot", "pizza"]
}
```

本地存储只保存合法配置。若用户将已有配置编辑到少于 3 个，保存按钮禁用，原有合法配置不被覆盖。

## 4. 菜单版本和失效处理

设置页加载当前菜单 Manifest 后校验本地 ID。创建房间时，客户端使用当前 Manifest 生成完整快照：

```ts
type CustomCatalogSnapshot = {
  catalogVersion: string;
  catalogHash: string;
  itemIds: string[];
  selectionHash: string;
};
```

`selectionHash` 由服务端根据规范化的 `catalogVersion`、`catalogHash` 和排序后的 `itemIds` 计算，用于识别不同房间的自定义列表。服务端不信任客户端传入的 Hash，收到请求后重新计算并校验。

如果菜单版本升级后某些 ID 不再存在：

1. 自动移除失效 ID。
2. 保留仍存在的 ID。
3. 剩余数量少于 3 个时，将本地配置标记为失效并提示重新配置。
4. 已创建的房间和已完成轮次继续使用它们各自冻结的旧菜单版本。

## 5. 房间和轮次生命周期

### 5.1 创建房间

组队模式自动创建房间时，客户端读取当前设备的自定义配置并随创建请求提交。没有合法自定义配置时，房间仍可创建，默认数据集为大类；房间中的自定义选项不可用并提示先去设置页配置。

后端校验 `itemIds` 数量、唯一性、菜单版本、菜单 Hash 和 ID 是否存在。校验通过后，将 `CustomCatalogSnapshot` 作为不可变房间配置保存。

### 5.2 等待房间

- 房间页可以在大类、小类和自定义之间切换。
- 切换数据集只修改 `selectedDataset`，不修改自定义快照。
- 房主不能在房间内编辑自定义菜品。
- 房间创建后，设置页的新修改不影响当前房间。
- 当前房间开放下一轮时继续使用原来的自定义快照。
- 想更换自定义列表，必须离开当前房间并创建新房间。

### 5.3 加入房间

客人加入时获取房主的完整自定义快照。客人的本地自定义列表不会被读取或覆盖。之后普通房间状态刷新和 WebSocket 通知只携带 `selectionHash`、数量和当前选择的数据集。

### 5.4 开始轮次

开始轮次时后端直接读取房间自定义快照，不要求客户端再次提交 `itemIds`。事务中将房间快照复制到轮次快照，并锁定菜单版本、菜单 Hash、数据集和成员集合。

轮次完成、刷新、断线重连和结果恢复都使用轮次快照。自定义菜品仍使用现有 `catalogItemId` 决定接口和结果聚合逻辑。

## 6. 数据模型

`rooms` 增加可空的 `custom_catalog` JSONB 字段，保存完整 `CustomCatalogSnapshot`。`rounds` 增加可空的 `custom_catalog` JSONB 字段，保存开始轮次时复制的快照。大类和小类轮次的该字段为空。

房间快照的常规状态响应只返回：

- `selectedDataset`。
- `customSelectionHash`。
- `customItemCount`。

创建房间和加入房间的入口响应包含完整快照。页面恢复时，如果客户端没有对应 Hash 的快照，再调用房间自定义菜单读取接口一次。后续状态刷新不重复返回完整 ID 列表。

## 7. API 和同步边界

创建房间请求增加可选 `customCatalog`。加入房间的入口响应返回房间元数据和完整自定义快照。增加只读的房间自定义菜单读取接口，用于刷新恢复或本地快照缺失时的单次补齐。

房间数据集修改接口只接受 `large`、`small` 或 `custom`，不接受自定义菜品 ID 列表。开始轮次接口不接受自定义菜品列表，服务端从房间配置读取。

WebSocket `room.updated` 事件不包含完整自定义列表；客户端通过房间 revision 和 `customSelectionHash` 判断是否需要补齐快照。自定义菜品 ID 是固定菜单中的公开 ID，不属于玩家隐私。

主要错误：

- `CUSTOM_CATALOG_TOO_SMALL`：少于 3 个菜品。
- `CUSTOM_CATALOG_INVALID`：包含重复、未知或不属于指定菜单版本的 ID。
- `CATALOG_HASH_MISMATCH`：菜单 Hash 校验失败。
- `CATALOG_VERSION_NOT_FOUND`：菜单版本不可用。
- `CUSTOM_CATALOG_IMMUTABLE`：尝试修改已创建房间的自定义快照。

## 8. 测试和验收

- 设置页少于 3 个时无法保存，已有合法配置不被覆盖。
- 设置页未保存返回会弹出确认框。
- 大类和小类可以混合选择并正确保存。
- 创建房间只提交一次自定义快照。
- 客人加入后得到与房主一致的 ID 列表。
- 房间状态刷新和 WebSocket 更新不重复携带完整 ID 列表。
- 切换房间数据集不会改变自定义快照。
- 房主本地设置变化不会影响已创建房间。
- 开始轮次使用房间快照，不接受客户端二次替换。
- 刷新、断线重连和结果页恢复仍使用同一份轮次快照。
- 删除或升级菜单条目后，本地配置按规则失效；旧房间和旧轮次仍可读取。
- 自定义菜品的多人结果继续使用现有交集和玩家明细聚合规则。
