# 今天吃什么 Web 版状态与状态转移设计

日期：2026-08-13

状态：已确认，作为多人房间、轮次和页面异常处理的状态行为入口

## 1. 文档目的

本文档定义应用在正常流程、刷新、断线、并发变化和服务端资源消失时的状态行为。

它解决的问题是：页面不能只根据 `loading`、`error`、`room` 等零散变量决定行为，也不能把“房间已经关闭”这类正常业务终态直接当成系统报错。

实现时应先根据服务端快照和 API 错误得到规范化状态，再由状态决定页面展示、可用操作和导航目标。

## 2. 与其他规格的关系

本项目的行为依据按以下顺序处理：

1. 用户最新确认。
2. 本状态设计。
3. `2026-08-12-food-game-e2e-design.md` 中的页面和产品流程。
4. `2026-08-12-food-game-multiplayer-technical-design.md` 中的服务端、同步和持久化约束。
5. 当前代码实现。

本文件专门描述状态、状态转移、容错和导航，不替代产品页面视觉规格，也不替代 API 数据结构和数据库设计。

## 3. 设计原则

- 服务端数据库是多人房间和轮次的最终事实来源。
- HTTP 快照用于恢复和确认真实状态；WebSocket 只负责提醒客户端重新读取快照。
- URL 中的房间 ID 或轮次 ID 只是查询线索，不代表资源仍然存在。
- 可以通过刷新快照恢复的错误，不直接显示为失败页面。
- 已关闭、已过期、已退出和已完成是可预期的业务状态，不是未分类异常。
- 页面动作使用明确的业务语义，例如“退出房间”“关闭房间”“返回房间”，不依赖 `navigate(-1)` 推断业务结果。
- 操作状态与业务状态分开维护。页面可以处于“房间等待中 + 正在提交退出操作”。
- 状态转换必须是可测试的纯逻辑；React 组件只负责渲染状态和发出动作。
- 当前 MVP 不引入 XState 等状态机库，使用 TypeScript 联合类型、状态解析器和错误分类器实现。

## 4. 状态分层

### 4.1 应用状态

应用状态负责匿名身份和启动时的房间恢复：

```text
booting
→ restoring-identity
→ restoring-room
→ ready-without-room
→ ready-with-room
```

异常状态：

```text
identity-retryable-error
room-retryable-error
```

身份恢复失败时不能读取或操作房间，应显示重试。查询当前房间返回不存在时，进入 `ready-without-room`，清理本地房间引用，并可以带一条“房间已关闭或过期”的提示。

### 4.2 房间状态

房间状态只描述当前用户与服务端房间的关系：

```text
none
restoring
waiting-host
waiting-guest
playing
results
closed
expired
unavailable
```

说明：

| 状态 | 含义 | 页面或后续动作 |
| --- | --- | --- |
| `none` | 当前用户没有有效房间 | 模式选择页 |
| `restoring` | 正在读取房间快照 | 房间恢复加载页 |
| `waiting-host` | 房间等待中，当前用户是房主 | 房主房间页 |
| `waiting-guest` | 房间等待中，当前用户是客人 | 客人房间页 |
| `playing` | 当前房间存在进行中的多人轮次 | 多人游戏页 |
| `results` | 当前轮次已完成，房间等待下一轮；暂不允许新成员加入 | 多人结果页或结果房间页 |
| `closed` | 房间被房主关闭或主动删除 | 清理本地引用，返回模式选择 |
| `expired` | 房间因长时间无业务活动被清理 | 清理本地引用，返回模式选择 |
| `unavailable` | 暂时无法判断房间状态 | 保留页面并允许重试 |

`closed` 和 `expired` 是正常业务终态，不应显示原始 404 或 500 信息。

### 4.3 轮次状态

轮次状态只描述当前用户在当前多人轮次中的进度：

```text
none
restoring
choosing
syncing
waiting-others
completed
removed
unavailable
```

说明：

| 状态 | 含义 | 页面 |
| --- | --- | --- |
| `none` | 当前没有可操作轮次 | 房间页或模式选择页 |
| `restoring` | 正在读取轮次和固定菜单 | 游戏恢复页 |
| `choosing` | 当前用户仍可继续选择 | 滑卡游戏页 |
| `syncing` | 本地选择已完成，正在等待队列同步和完成请求 | 同步状态页或轻量遮罩 |
| `waiting-others` | 当前用户已完成，其他有效成员尚未完成 | 等待伙伴页 |
| `completed` | 服务端已生成冻结结果 | 多人结果页 |
| `removed` | 当前用户被房主移出本轮 | 本轮已结束提示页 |
| `unavailable` | 轮次不存在或暂时无法恢复 | 根据最新房间状态重新导航 |

### 4.4 操作状态

操作状态不能和页面业务状态混用：

```text
idle
submitting
refreshing
retryable-error
success
```

例如：

```text
room = waiting-guest
action = submitting
actionName = leave-room
```

提交操作期间只禁用相关按钮，不应让整个页面进入无内容的全屏 loading。

## 5. 状态解析规则

页面不直接组合多个布尔变量，而是使用规范化解析：

```text
身份快照 + 当前房间快照 + 当前轮次快照
→ normalizeAppState()
→ AppState
→ 页面投影和可用动作
```

房间快照解析规则：

1. 无房间响应 → `none`。
2. 房间存在且 `status=waiting`，当前用户是房主 → `waiting-host`。
3. 房间存在且 `status=waiting`，当前用户是客人 → `waiting-guest`。
4. 房间存在且 `status=playing`，有 `currentRoundId` → `playing`，继续解析轮次。
5. 房间存在且 `status=results`，有 `currentRoundId` → `results`。
6. 资源明确不存在或已关闭 → `closed` 或 `expired`。
7. 网络错误、超时或未知服务端错误 → `unavailable`，保留重试能力。

轮次快照解析规则：

1. `snapshot.status=playing` 且自己的成员状态为 `choosing` → `choosing`。
2. 本地决定全部产生但仍有未确认队列或完成请求 → `syncing`。
3. 自己的成员状态为 `completed`，轮次仍为 `playing` → `waiting-others`。
4. 轮次状态为 `completed` → `completed`。
5. 自己的成员状态为 `removed` → `removed`。
6. 轮次不存在、轮次已结束或房间状态已变化 → 重新查询房间，再决定导航。

## 6. 页面状态矩阵

| 页面 | 主要状态 | 可执行动作 | 失败后的默认处理 |
| --- | --- | --- | --- |
| 首页 | 编辑中、用户名为空、提交中 | 修改用户名、开始游戏 | 留在首页，显示具体提示 |
| 模式选择 | 正常、创建房间中、已有房间恢复中 | 单人、组队、返回首页 | 创建失败留在当前页，可重试 |
| 房主房间 | 恢复中、等待中、操作中、已关闭 | 修改数据集、加入其他房间、开始、关闭 | 关闭时房间不存在视为已关闭成功 |
| 客人房间 | 恢复中、等待中、操作中、已关闭 | 退出房间、等待房主开始 | 房间不存在视为已经退出 |
| 加入房间弹窗 | 编辑中、校验中、加入中、加入失败 | 输入、加入、取消 | 输入错误留在弹窗，加入失败保留输入 |
| 数据集页 | 加载中、可选择、加载失败、启动中 | 选择大类/小类、返回 | 加载失败显示重试和返回 |
| 多人游戏页 | 恢复中、选择中、同步中、等待其他人、已移出 | 喜欢、不喜欢、撤销、返回房间 | 可恢复错误重新获取快照 |
| 等待伙伴页 | 等待中、全部完成、房间失效 | 查看进度、返回房间 | 房间失效清理本地状态并离开 |
| 多人结果页 | 加载中、正常、空交集、结果失效 | 查看结果、返回房间 | 结果失效时查询房间最新状态 |
| 单人结果页 | 加载中、正常、空结果 | 查看清单、返回模式选择 | 本地数据异常时允许返回或重试 |

## 7. 页面和状态转移

### 7.1 应用启动和恢复

```text
启动
→ 恢复匿名身份
→ 查询当前房间
```

结果：

| 查询结果 | 处理 |
| --- | --- |
| 无房间 | 进入模式选择 |
| `waiting` | 进入对应房主/客人房间页 |
| `playing` | 进入多人游戏页 |
| `results` | 进入多人结果页 |
| 房间不存在 | 清除本地房间信息，进入模式选择并提示 |
| 网络失败 | 显示恢复失败和重试，不清除可能仍有效的本地信息 |

### 7.2 房主创建、等待和关闭

```text
模式选择
→ 创建房间中
→ waiting-host
```

房主关闭房间：

```text
waiting-host
→ submitting close-room
→ 成功
→ none
→ 模式选择
```

如果关闭接口返回 `ROOM_NOT_FOUND`、`ROOM_CLOSED` 或等价的资源不存在错误：

```text
→ 视为关闭已完成
→ 清除本地房间引用
→ none
→ 模式选择
→ 提示“房间已关闭”
```

### 7.3 客人加入和退出

```text
加入弹窗
→ 校验房间号
→ 加入中
→ waiting-guest
```

客人退出：

```text
waiting-guest
→ 确认退出
→ submitting leave-room
→ 成功
→ none
→ 模式选择
```

如果房间已被关闭或已过期：

```text
ROOM_NOT_FOUND / ROOM_CLOSED / ROOM_EXPIRED
→ 视为退出完成
→ 清除本地房间引用
→ none
→ 模式选择
→ 提示“房间已关闭”
```

### 7.4 开始多人轮次

```text
waiting-host
→ submitting start-round
→ 服务端事务锁定成员、菜单版本和数据集
→ playing
→ restoring round
→ choosing
```

房主收到 `ROOM_REVISION_CONFLICT` 时：

```text
→ 获取最新房间快照
→ 如果仍是 waiting-host，允许用户重新确认并开始
→ 如果已经 playing，进入多人游戏
→ 如果已经 results，进入结果页
```

不能把 revision 冲突直接展示成不可恢复错误。

### 7.5 多人选择和完成

```text
choosing
→ 本地记录喜欢/不喜欢
→ 发送队列同步
→ choosing
```

最后一项选择后：

```text
所有项目已决定
→ syncing
→ 等待发送队列清空
→ 提交完成轮次
```

服务端结果：

| 响应 | 下一状态 |
| --- | --- |
| 轮次仍为 `playing` | `waiting-others` |
| 轮次为 `completed` | 多人结果页 |
| `ROUND_REVISION_CONFLICT` | 重新获取轮次快照，再按最新状态判断 |
| `ROUND_NOT_PLAYING` | 查询房间和轮次最新状态 |
| `ROUND_NOT_FOUND` | 查询房间；结果状态进入结果页，否则返回房间或模式选择 |
| 网络错误 | 保留未确认队列，显示可重试同步状态 |

### 7.6 等待伙伴和自动进入结果

等待页至少展示：

```text
你已完成选择
2 / 3 人已完成

房主    已完成
玩家 A  已完成
玩家 B  选择中

[返回房间]
```

点击“返回房间”只改变页面位置，不退出房间，不删除本轮选择：

```text
waiting-others
→ 房间页，房间仍为 playing
```

如果 WebSocket 或重新读取发现所有成员已经完成：

```text
waiting-others
→ completed
→ 多人结果页
```

如果房主移出未完成成员，服务端完成轮次：

```text
waiting-others
→ completed
→ 多人结果页
```

### 7.7 多人结果和下一轮

```text
completed
→ 多人结果页
→ 返回房间
→ results
```

房主：

```text
results
→ submitting open-next-round
→ waiting-host
```

客人：

```text
results
→ waiting-guest
```

结果页返回房间不应依赖浏览器历史；必须使用当前结果中的 `roomId` 进行明确导航。

## 8. API 错误分类和处理

### 8.1 正常业务终态

这些错误代表资源已经达到不可继续操作的状态：

| 错误 | 业务含义 | 客户端处理 |
| --- | --- | --- |
| `ROOM_NOT_FOUND` | 房间已关闭、过期或不存在 | 清除本地房间，返回模式选择 |
| `ROOM_CLOSED` | 房间已经关闭 | 同上 |
| `ROOM_EXPIRED` | 房间已过期 | 同上 |
| `ROUND_NOT_FOUND` | 轮次不存在 | 查询房间最新状态 |
| `ROUND_NOT_PLAYING` | 轮次已经结束 | 查询最新轮次和房间状态 |
| `RESULT_NOT_FOUND` | 结果尚未可读或轮次已失效 | 查询最新状态，不能直接白屏 |

### 8.2 可以恢复的并发状态

| 错误 | 处理 |
| --- | --- |
| `ROOM_REVISION_CONFLICT` | 获取最新房间快照，根据最新状态继续 |
| `ROUND_REVISION_CONFLICT` | 获取最新轮次快照，合并本地未发送操作后继续 |
| `ROOM_NOT_JOINABLE` | 留在加入弹窗，显示房间已开始、已满员或不可加入 |
| `HOST_ONLY` | 留在当前页，提示只有房主可以执行该操作 |
| 已有房间 | 显示继续当前房间或明确恢复当前房间，不重复创建隐形房间 |

### 8.3 临时和系统错误

| 类型 | 示例 | 处理 |
| --- | --- | --- |
| 身份失效 | `401` | 自动恢复身份并重试一次；仍失败则回到启动恢复 |
| 网络错误 | 超时、断网、连接关闭 | 保留当前业务状态，显示重试和同步提示 |
| 输入错误 | 房间号格式错误、用户名为空 | 留在当前表单并显示具体原因 |
| 限流 | `429` | 显示稍后重试，避免自动快速循环 |
| 服务端异常 | `500`、未知错误 | 保留当前页面，显示通用错误和重试 |

所有未识别错误必须记录 request ID（如果有），但用户界面不展示堆栈、原始 JSON 或内部错误信息。

## 9. 返回和离开规则

| 页面或状态 | 返回行为 |
| --- | --- |
| 首页 | 无标准返回 |
| 模式选择 | 返回首页 |
| 数据集页 | 返回模式选择 |
| 房主房间页 | 确认后关闭房间 |
| 客人房间页 | 确认后退出房间 |
| 加入房间弹窗 | 取消并关闭弹窗 |
| 多人游戏选择中 | 不显示标准顶部返回，避免误丢选择 |
| 多人游戏已完成 | 进入等待伙伴页，不直接返回模式选择 |
| 等待伙伴页 | 返回房间，不退出房间 |
| 多人结果页 | 返回房间 |
| 单人结果页 | 返回模式选择 |

房主关闭房间和客人退出房间都必须经过确认。接口已经表明资源不存在时，操作按幂等成功处理。

## 10. 本地状态清理规则

进入 `none`、`closed` 或 `expired` 时清理：

- 当前房间 ID 引用；
- 当前轮次 ID 引用；
- 当前房间角色缓存；
- 已失效的房间恢复标记。

多人本轮的本地决定队列只有在以下情况清理：

- 服务端确认操作已落库并从队列删除；
- 轮次完成且队列为空；
- 当前用户被移出本轮，服务端确认删除其本轮决定；
- 轮次或房间已经明确失效。

网络错误和普通页面返回不能清理未确认的决定队列。

## 11. 实现边界

建议拆分为以下纯职责模块：

```text
state-types.ts       状态联合类型和动作类型
state-normalizer.ts  快照/错误 → 规范化状态
error-policy.ts      API 错误 → 业务处理策略
navigation-policy.ts 状态/动作 → 明确导航目标
```

React hook 负责：

- 调用 API；
- 保存当前快照；
- 订阅 WebSocket；
- 调用状态解析器；
- 暴露状态和业务动作。

页面组件负责：

- 根据状态渲染内容；
- 显示动作提交中、可重试和成功提示；
- 调用明确动作，不直接解析底层 API 错误。

当前阶段不建立一个跨应用、跨页面的大型 reducer，也不把单人本地游戏强行接入多人房间状态机。单人游戏保留自己的本地轮次状态，但沿用相同的加载、空数据、错误和返回语义。

## 12. 验收场景

实现状态系统后至少验证：

1. 房间已关闭时，房主再次点击“关闭房间”不会出现原始接口报错。
2. 房间已关闭时，客人点击“退出房间”会按退出成功处理并回到模式选择。
3. 刷新已关闭房间 URL 会进入模式选择，并提示房间已关闭。
4. 房主开始游戏时，客人房间页能进入多人游戏，不停留在旧等待页。
5. 用户完成选择但其他人未完成时，进入等待伙伴页并展示成员状态。
6. 等待伙伴页点击“返回房间”不会退出房间或删除选择。
7. 其他成员完成后，等待页和房间页都能进入结果页。
8. 结果页点击“返回房间”始终进入当前轮次的结果房间，而不是依赖浏览器历史。
9. 结果房间中房主可以开始下一轮，客人看到等待房主提示。
10. 网络临时失败时保留当前页面和未确认操作，恢复后可以继续。
11. revision 冲突会读取最新状态，不展示不可恢复错误。
12. 房间关闭、过期、轮次完成等正常终态不会显示技术堆栈或原始错误对象。
