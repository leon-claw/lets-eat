# 今天吃什么 Web 版端到端产品与交互规格

日期：2026-08-12

状态：已确认的 MVP 产品规格，已同步固定菜品库、二元选择、多人流程和交集结果变更

## 1. 文档目的

本文档将已经确认的端到端原型同步到项目本地，使开发 Agent 在无法读取 Figma、Figma 调用额度不足或原型节点变化时，仍能准确理解目标产品。

本文档描述目标产品行为和页面流程，不等同于当前代码的实现状态。未经用户确认，不得根据现有代码、旧 README 或个人推断改变本文档中的产品规则。

## 2. 事实来源与冲突处理

信息冲突时按以下优先级处理：

1. 用户在当前任务中的最新明确确认。
2. 本文档。
3. Figma 原型中的视觉布局、尺寸和层级。
4. 当前代码、测试、README 和旧设计文档。

Figma 是视觉参考，不是业务规则的唯一来源。现有代码代表已经实现的能力，不自动代表目标产品行为。

## 3. 产品目标

产品帮助一个人或一组人通过浏览和选择菜品，快速决定“今天吃什么”。

第一阶段为完整 Web 版体验，优先验证以下闭环：

- 用户进入应用并设置显示名称。
- 用户选择单人游戏或组队游戏。
- 组队用户创建、加入和等待房间。
- 用户选择可用的菜品数据集。
- 用户通过左右滑动浏览并选择菜品。
- 用户结束选择后查看结果，组队时等待其他成员完成。

本文档不要求开发微信小程序，也不要求在本轮接入附近餐厅、地图、外卖、订单或支付能力。

## 4. 核心产品规则

### 4.1 用户名

- 首页进入时随机生成一个可读的默认用户名。
- 用户名输入框可以编辑。
- 用户名用于房间成员列表和“自己”的身份标记。
- 进入游戏流程前用户名不能为空；空值时留在首页并提示用户填写。

### 4.2 菜品库

- MVP 使用应用内置的只读固定菜品库；自定义菜品只是从该库中选择的子集，不会产生新的菜品数据。
- 所有用户共享同一份全局固定菜品库，不存在可编辑的用户个人菜品库或房主私有菜品库。
- 用户不能新增、编辑、删除菜品，也不能上传或更换菜品图片；用户只能在设置页保存由固定菜品 ID 组成的自定义选择。
- 菜品库只能随应用版本发布而更新，不提供运行时管理入口。
- 每条菜单数据至少包含：唯一标识、图片字段、名称、说明、数据集类型和固定顺序；图片暂未配置时使用留白占位，不阻断游戏。
- 全局固定菜单包含“大类菜品”和“小类菜品”两个独立集合；“自定义菜品”是房间级选择，不是第三个可发布的菜单集合。
- 大类菜品表示料理体系、地域风格或国家风味，例如粤菜、川菜、日料、西餐和东南亚菜。
- 小类菜品表示具体餐饮品类，例如火锅、螺蛳粉、麻辣烫、寿司、披萨和咖啡。
- 两个数据集彼此独立，没有父子关联，也不自动联动。
- 小类菜品可以通过 `cuisineTags` 关联 0～3 个大类菜品 ID，用于展示、统计和未来筛选；该标签关系不改变两个数据集的独立选择规则。
- 卡片辅助字段包括展示标签和代表食物，不参与多人结果计算。

### 4.5 自定义菜品

- 用户在设置页从当前固定菜单中选择自定义菜品，允许混合大类和小类。
- 自定义列表至少包含 3 个菜品，少于 3 个时不能保存。
- 设置页使用草稿状态；未保存返回时必须确认，非法草稿不能覆盖已有合法配置。
- 自定义列表只保存在当前设备，不进行账号同步，也不在设置过程中请求后端。
- 房主创建房间时读取当前设备配置并提交一次；房间创建后该列表冻结。
- 房主、客人和设置页的后续变化都不影响已经创建的房间；要更换列表必须创建新房间。
- 客人使用房主的房间级自定义列表，不使用自己的本地自定义列表。

### 4.3 游戏选择

- 游戏主页保留现有版本已经验证过的叠卡和滑动体验。
- 左滑或点击“不喜欢”表示不选中当前菜品。
- 右滑或点击“喜欢”表示选中当前菜品。
- 游戏不提供“强推”和上滑选择手势。
- 用户可以撤销上一次有效选择操作。
- 动画期间锁定重复操作，避免同一张卡被处理多次。
- 游戏主页不显示“2人想吃”或其他实时想吃人数文案。
- 游戏主页不提供“摇号”功能。
- 游戏主页是沉浸式游戏页面，不显示标准顶部返回按钮。

### 4.4 返回规则

- 首页没有返回按钮。
- 游戏主页没有标准顶部返回按钮。
- 其他所有完整页面均在顶部提供明确的返回入口。
- 弹窗必须提供关闭或取消入口，其语义等同于返回上一层。
- 返回操作不得无提示地丢失已经保存的数据。

## 5. 页面清单

目标产品包含 9 个完整页面和 1 个弹窗，共 10 个页面或独立状态：

1. 首页。
2. 游戏模式选择页。
3. 房间匹配页（房主）。
4. 加入房间弹窗。
5. 房间匹配页（客人）。
6. 菜品数据集确认页。
7. 游戏主页。
8. 游戏结束结果页。
9. 游戏结束等待伙伴页。
10. 设置页（自定义菜品）。

## 6. 页面详细规格

### 6.1 首页

从上到下包含：

- 大 Logo。
- 用户名输入框，随机初始化且可以编辑。
- 主按钮“开始游戏”。
- 右上角设置入口，进入设置页。

交互：

- 点击“开始游戏”进入游戏模式选择页。
- 用户名为空时不进入下一页，并显示明确提示。

### 6.2 游戏模式选择页

包含：

- 顶部返回按钮。
- “单人游戏”按钮。
- “组队游戏”按钮。

交互：

- “单人游戏”进入菜品数据集确认页，由用户选择本轮使用的大类或小类菜品。
- “组队游戏”读取当前设备的自定义菜品配置，并进入房间匹配页（房主）创建房间；创建请求一次性提交自定义快照。
- 返回首页时保留当前用户名。

### 6.3 房间匹配页（房主）

进入页面时自动创建一个房间，当前用户成为房主。

从上到下包含：

- 顶部返回按钮。
- 页面标题。
- 当前房间号。
- 当前菜品数据集，默认选择“大类菜品”。
- “大类菜品”“小类菜品”和“自定义菜品”切换控件，以及不可用的“周围菜品”入口。
- “加入房间”按钮。
- “开始游戏”按钮。
- 已加入成员列表。

房间规则：

- 房间号是随机生成的 4 位数字。
- 成员列表包含房主和已经加入的客人，并明确标记房主。
- 房主可以在本轮开始前切换菜品数据集；自定义菜品列表不在房间内编辑，而是在创建房间时已经冻结。
- 当前设备没有至少 3 个已保存的自定义菜品时，“自定义菜品”不可用，并提示先去设置页配置。
- 点击“加入房间”打开加入房间弹窗，用于放弃当前房主房间并加入他人的房间。
- 创建新房间或加入他人房间时，如果当前身份仍属于其他房间，服务端自动在同一事务中清理旧房间关系：客人退出旧房间，房主关闭旧房间；房主关闭旧房间会使旧房间的其他成员一起退出。
- 点击“开始游戏”后直接锁定当前成员、菜单版本、数据集和房间自定义快照，并使所有成员进入游戏主页。
- 返回模式选择页视为离开并关闭当前房间；执行前应给出确认，避免误操作。

### 6.4 加入房间弹窗

包含：

- 标题。
- 4 位房间号输入框。
- “加入”按钮。
- 关闭或取消入口。

交互：

- 仅接受 4 位数字。
- 输入无效时留在弹窗并显示原因。
- 加入成功后进入房间匹配页（客人）。
- 取消后关闭弹窗并返回原房主页面，不改变当前房间状态。

### 6.5 房间匹配页（客人）

从上到下包含：

- 顶部返回按钮。
- 页面标题和当前房间号。
- “退出房间”按钮。
- “待房主开始”提示语。
- 房主当前选择的菜品数据集，只读展示。
- 如果房主选择自定义菜品，只读展示自定义菜品数量，不展示完整清单。
- 成员列表。

交互：

- 成员列表明确标记当前用户“我”和房主。
- 客人不能开始游戏或更改数据集。
- 房主切换数据集时，客人实时看到最新选择；房间级自定义菜品快照不可修改。
- 房主开始游戏后，所有客人进入同一轮游戏。
- 点击“退出房间”或顶部返回按钮均需确认；确认后回到游戏模式选择页。

### 6.6 菜品数据集确认页

该页面只用于单人模式，包含三个选择按钮：

- “大类菜品”：提示“西餐、中餐、日料等大分类”，并展示当前可用数据条数。
- “小类菜品”：提示“螺蛳粉、火锅、披萨等小分类”，并展示当前可用数据条数。
- “周围菜品”：提示“待上线，点击催开发进度”。

交互：

- 顶部返回按钮返回游戏模式选择页。
- 选择“大类菜品”或“小类菜品”后启动单人轮次并进入游戏主页。
- 数据条数必须来自内置固定菜品库，不能写死为与实际数据不一致的数字。
- “周围菜品”当前不可启动游戏；点击后只展示待上线反馈，不发起地图或餐厅接口请求。

### 6.7 游戏主页

页面沿用当前已经确认的滑卡视觉和交互效果，至少包含：

- 当前进度。
- 当前菜品卡和下一张卡的叠放预览。
- 菜品图片、名称、说明、分类或代表食物信息。
- 撤销、不喜欢和喜欢操作。

页面不包含：

- 标准顶部返回按钮。
- “2人想吃”文案。
- 摇号按钮或任何等价的随机决策入口。
- 强推按钮或上滑选择手势。

完成规则：

- 看完本轮全部菜品后结束当前用户的选择。
- 单人游戏直接进入游戏结束结果页。
- 组队游戏在当前用户完成而其他成员尚未全部完成时，进入等待伙伴页。
- 组队游戏全部有效成员完成后进入游戏结束结果页。

### 6.8 游戏结束等待伙伴页

用于组队模式，表示当前用户已经完成选择，但房间内仍有人未完成。

包含：

- 顶部返回按钮。
- “等待其他小伙伴”提示。
- 已完成人数与总人数，例如“2 / 3 人已完成”。
- 成员列表和每个成员的“已完成”“选择中”或“已移出本轮”状态。
- 当前用户标记。
- “返回房间”按钮。
- 房主可见的“移出本轮”操作，用于处理长期无响应且未完成的成员。

交互：

- 所有成员完成后自动进入游戏结束结果页。
- 点击顶部返回或“返回房间”回到当前房间页，不删除已经提交的本轮选择。
- 房主将成员移出本轮后，该成员本轮选择被删除且不参与结果统计；成员关系仍保留，可参加下一轮。
- 等待页不提供摇号功能。

### 6.9 游戏结束结果页

包含：

- 顶部返回按钮。
- 完成提示和本轮选择摘要。
- 查看备选清单入口。
- 返回入口。

规则：

- 不显示摇号按钮或任何等价的随机决策入口。
- 单人模式的返回入口回到游戏模式选择页。
- 组队模式的返回入口显示“返回房间”，回到当前房间页。
- 单人结果只展示本轮喜欢的菜品。
- 组队结果顶部展示所有有效玩家都喜欢的菜品交集，按固定菜单顺序排列。
- 组队结果下方按玩家展示每位有效玩家各自喜欢的菜品，玩家顺序按加入房间顺序排列。
- 组队结果展示玩家显示名称和其喜欢的菜品，不展示逐项“不喜欢”记录。
- 被移出本轮的玩家不参与交集，也不出现在玩家明细中。
- 组队结果在轮次完成时生成并冻结结果快照；成员之后退出房间不会改变已经生成的结果。
- 没有共同喜欢的菜品时，顶部展示明确的空交集提示；不进行随机兜底。

### 6.10 设置页（自定义菜品）

包含：

- 顶部返回按钮。
- “自定义菜品”标题和已选数量，例如“已选 12/53”。
- “全部 / 大类 / 小类”筛选。
- 带图片、名称和数据集标签的复选列表。
- 底部固定保存按钮。

交互：

- 筛选只影响展示，不限制大类和小类混合选择。
- 少于 3 个菜品时保存按钮不可用，并提示“至少选择 3 道菜品”。
- 保存成功后仅更新当前设备的合法配置。
- 编辑已有配置时，如果草稿少于 3 个，原有配置保持不变。
- 有未保存修改时返回，必须通过确认框确认离开。
- 菜单版本更新后自动移除失效 ID；剩余少于 3 个时提示重新配置。

## 7. 端到端流程

### 7.1 单人游戏

```text
首页
→ 游戏模式选择
→ 单人游戏
→ 菜品数据集确认
→ 游戏主页
→ 游戏结束结果页
→ 游戏模式选择
```

### 7.2 组队游戏（房主）

```text
首页
→ 游戏模式选择
→ 创建房间并成为房主（提交已保存的自定义快照）
→ 等待客人加入
→ 在房间页确认或修改菜品数据集
→ 开始游戏
→ 游戏主页
→ 等待伙伴（仅其他成员未完成时）
→ 游戏结束结果页
→ 返回房间
```

### 7.3 组队游戏（客人）

```text
房主房间页
→ 加入房间弹窗
→ 输入他人房间号
→ 客人房间页
→ 等待房主开始
→ 游戏主页
→ 等待伙伴（仅其他成员未完成时）
→ 游戏结束结果页
→ 返回房间
```

## 8. 状态和边界处理

- 数据加载中必须显示明确的加载状态，不能展示空白页面。
- 固定菜品数据加载失败或为空时不能进入游戏轮次，应提示数据异常并允许重试或返回数据集选择页。
- 图片加载失败时显示稳定的占位图，不显示破损图标。
- 快速重复点击或滑动不得重复提交同一操作。
- 房间号错误、房间不存在、房间已关闭或加入失败时，留在加入弹窗并显示具体错误。
- 房间最多 8 人（含房主）；满员后拒绝新成员加入。
- 当前轮次开始后暂停新成员加入，本轮结束并回到房间后重新开放。
- 本轮完成后房间先进入结果状态；房主返回房间并开放下一轮后，才重新允许加入和修改数据集。结果页返回房间后，当前用户仍可通过“加入房间”入口加入另一个房间。
- 房主离开、客人离开和成员状态变化应在成员列表中得到反馈。
- 临时断线不自动退出房间或轮次；刷新和重连后恢复当前身份、角色和进度。
- 创建新房间或加入已有房间不需要额外的替换标记，服务端会先校验目标房间，再自动切换当前身份所属房间。
- 房主主动关闭房间时销毁房间数据；连续 24 小时无操作的房间自动清理。
- 自定义菜品少于 3 个时不能在设置页保存；房间创建时也必须由服务端再次校验。
- 房间创建后自定义菜品快照不可修改；设置页后续变化只对新创建的房间生效。
- 客人加入时获得房主的自定义快照，客人的本地自定义配置不参与当前房间。
- 每位成员在结果生成前只能读取和修改自己的选择；其他成员只能看到“选择中”或“已完成”。
- 当前规格定义产品状态，不强制指定多人同步的服务端技术方案；技术设计必须实现上述用户可见行为，不能用会改变体验的临时方案代替。
- 多人结果采用所有有效玩家喜欢菜品的严格交集，并同时展示每位有效玩家各自喜欢的菜品明细；不引入权重，也不随机替用户做决定。

## 9. MVP 范围外

本阶段不包含：

- 微信小程序。
- 周围餐厅或地图接口的真实接入。
- 外卖平台、菜单、价格、优惠券、订单和支付。
- 社交账号登录。
- 菜品库管理、菜品新增、编辑、删除和图片上传。
- 摇号、随机转盘或随机替用户做最终决定。
- 大类菜品与小类菜品的父子关系。
- 未经确认的推荐算法和偏好画像。

## 11. 实现约束

- 第一实现目标必须是可端到端运行的最小闭环。
- 保留当前已经验证过的滑卡组件和交互效果，避免重写造成体验回退。
- 页面、房间、固定菜品库和游戏状态保持明确边界。
- 固定菜品库作为只读发布资源，不为 MVP 建立菜品管理接口、数据库写入流程或图片上传链路。
- 优先复用项目已有依赖和成熟库；添加依赖前检查现有依赖、文档和类型定义。
- 不为未确认的未来需求增加抽象层。
- 不采用明确计划以后整体替换的临时架构。

## 12. 验收标准

- 后续 Agent 无需读取 Figma，也能仅凭本文档列出所有页面和完整流程。
- 首页与游戏主页没有标准顶部返回按钮，其余页面有明确返回或关闭入口。
- 游戏主页不显示“2人想吃”，游戏主页和结果页均无摇号功能。
- 首页有设置入口；设置页只允许编辑当前设备的自定义菜品选择，不提供菜品库管理、编辑菜品或新增菜品页面。
- 所有用户使用同一份只读固定菜品库，应用内不能修改菜品或图片。
- 单人游戏先进入菜品数据集确认页；多人房主在房间页选择数据集，默认选择“大类菜品”。
- 游戏只包含喜欢、不喜欢和撤销，不包含强推或上滑选择。
- 组队用户完成选择但仍有人未完成时进入等待伙伴页。
- 大类菜品和小类菜品始终作为两个互不关联的数据集处理。
- 组队结果展示有效玩家喜欢菜品的交集，以及每位有效玩家各自喜欢的菜品明细；被移出玩家不参与结果。
- 单人和组队流程都能形成明确闭环。
- Figma 与本文档出现业务冲突时，实现遵循本文档。
