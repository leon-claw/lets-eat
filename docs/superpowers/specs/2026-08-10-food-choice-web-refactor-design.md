# 饮食选项 Web 版领域化重构设计

日期：2026-08-10

## 1. 背景

`source` 目录当前是一套由 React、TypeScript、Vite、Tailwind CSS 和 Motion 构建的移动端 Web 原型。原型以具体菜品为核心，包含刷卡、收藏、随机决策、优惠券、订单、设置和底部导航等模拟功能。

本次重构将它收敛为一个可长期扩展的单页 Web 产品。第一版帮助用户在混合饮食分类中快速决定“今天吃什么”，选择对象包括粤菜、火锅、烧烤、螺蛳粉、轻食和日料等。未来再从选中的饮食分类扩展到附近餐厅。

## 2. 目标

- 将核心领域从具体菜品 `Dish` 改为饮食选项 `FoodChoice`。
- 使用领域化目录组织应用、实体、功能和共享代码。
- 页面只保留饮食选项刷卡与选择结果。
- 左滑表示跳过，右滑表示选定。
- 同时提供按钮操作，保证桌面端无需拖拽也能完成选择。
- 第一版使用本地模拟数据，但通过仓储接口隔离数据来源。
- 为未来增加附近餐厅入口保留稳定的领域边界。
- 保持移动端优先，同时在桌面端居中正常展示。
- 建立业务逻辑测试、类型检查、生产构建和浏览器验证流程。

## 3. 非目标

本次不实现以下功能：

- 高德或其他地图接口。
- 餐厅搜索和餐厅列表。
- 收藏、历史记录或用户偏好持久化。
- 随机转盘。
- 优惠券、订单、设置和底部导航。
- 登录、账号、后端服务和数据库。
- 微信小程序。

## 4. 核心领域模型

第一版使用统一的 `FoodChoice` 模型承载传统菜系和具体品类：

```ts
interface FoodChoice {
  id: string;
  name: string;
  description: string;
  coverImage: string;
  tags: string[];
  representativeFoods: string[];
}
```

模型不包含价格、月售、配送费、起送价、配送时间和商家评分等餐厅或外卖字段。未来新增 `Restaurant` 实体时，通过 `foodChoiceIds` 与一个或多个饮食选项建立关联，不改变第一版选择流程的核心模型。

## 6. 数据访问

饮食选项通过 `FoodChoiceRepository` 获取：

```ts
interface FoodChoiceRepository {
  list(): Promise<FoodChoice[]>;
}
```

第一版提供 `mockFoodChoiceRepository`，从本地模拟数据返回结果。`useChooseFood` 通过依赖注入接收仓储，不直接导入模拟数据。未来接入服务端时替换仓储实现，不修改刷卡页面和状态规则。

数据流如下：

```text
App
  → useChooseFood
    → FoodChoiceRepository
      → mockFoodChoiceRepository
```

## 7. 页面状态与交互

页面状态包括：

- `loading`：正在加载饮食选项。
- `choosing`：正在浏览和选择。
- `selected`：已经右滑或点击选定某个饮食选项。
- `exhausted`：所有选项都已被跳过。
- `empty`：仓储成功返回，但没有可用饮食选项。
- `error`：数据加载失败。

交互规则：

- 初始化成功后随机打乱饮食选项。
- 左滑或点击“换一个”跳过当前选项。
- 右滑或点击“就吃这个”选定当前选项。
- 选定后停止处理其他滑动和按钮事件。
- 结果状态展示名称、简介、标签和代表食物。
- 点击“重新选择”重新打乱全部选项并回到第一张。
- 所有选项被跳过后进入 `exhausted`，允许重新开始。
- 动画进行期间锁定当前操作，避免快速连续触发造成状态重复更新。

## 8. 界面设计

页面维持移动端优先的卡片体验：

- 顶部使用黄色简洁标题栏，显示“今天吃什么”。
- 选择状态显示当前进度，例如“3 / 20”。
- 主区域一次只显示一个饮食选项。
- 卡片包含封面、名称、简介、标签和代表食物。
- 卡片下方提供“换一个”和“就吃这个”按钮。
- 支持鼠标拖拽和触摸滑动。
- 结果状态只展示已选饮食选项和“重新选择”按钮。
- 桌面端使用受控最大宽度居中，移动端占满可用宽度和高度。

## 9. 错误与边界处理

- 图片加载失败时使用渐变占位背景，不显示破损图片图标。
- 仓储返回空数组时显示空状态和重试按钮。
- 仓储抛出错误时进入错误状态并提供重试。
- 全部选项被跳过时显示完成状态并允许重新开始。
- 组件卸载后不更新异步加载状态。
- 重试、重新开始和选定操作在动画锁定期间不可重复触发。

## 10. 项目清理

在删除旧原型组件前，先将当前 `source` 目录作为原型快照提交到 Git，确保所有原始代码可恢复。

重构期间执行以下清理：

- 删除不再使用的旧菜品模型和模拟菜品数据。
- 删除收藏、随机转盘、优惠券、订单、设置和底部导航组件。
- 删除 AI Studio 专用的元数据、目录和旧环境变量说明。
- 移除未使用的 Gemini、Express、dotenv、tsx 和 Express 类型依赖。
- 保留 React、React DOM、TypeScript、Vite、Tailwind CSS、Motion 和图标依赖。
- 更新项目名称、README、本地启动命令和验证命令。
- 保留并提交依赖锁文件，确保安装结果可复现。

## 11. 测试与验证

为纯业务逻辑建立单元测试，至少覆盖：

- 初始化后返回完整且不重复的饮食选项序列。
- 跳过后正确前进到下一项。
- 选定后进入 `selected` 并保留正确结果。
- 全部跳过后进入 `exhausted`。
- 重新开始后清空结果并生成新一轮序列。
- 空数据和仓储错误进入正确状态。
- 动画锁定期间忽略重复操作。

交付前执行：

```text
npm run test
npm run lint
npm run build
npm run dev
```

最后在真实浏览器中验证：

- 鼠标拖拽和按钮操作。
- 左滑、右滑、选定结果和重新开始。
- 图片失败占位、空状态和错误状态。
- 桌面尺寸与移动端尺寸无明显溢出。

## 12. 验收标准

- 应用只有一个饮食选择页面，没有底部导航和旧业务入口。
- 用户可以通过左滑或按钮跳过当前饮食选项。
- 用户可以通过右滑或按钮选定当前饮食选项。
- 选定后显示结果并可以重新开始。
- 模拟数据、业务状态和 UI 组件位于明确的领域边界中。
- 旧原型已通过 Git 快照保留。
- 单元测试、类型检查和生产构建全部通过。
- 项目可通过 README 中的命令在本地启动。
