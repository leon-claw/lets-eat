# 多人模式“周围菜品”设计

日期：2026-09-14

状态：已确认，供实现计划和开发使用

## 1. 目标

将已经验证过的“周围菜品”搜索、分类和门店聚合能力接入多人房间，使房主可以使用自己的位置生成一份附近菜品数据，所有成员随后使用同一份冻结数据完成多人游戏。

本设计遵循以下优先级：

1. 用户在本设计中的最新确认。
2. 本项目已有的端到端产品规格和多人技术设计。
3. 现有代码和历史行为。

本设计更新了早期“多人流程不支持周围菜品”的 MVP 边界。单人周围菜品流程仍然保留，新增的是多人房间级的周围菜品数据集。

## 2. 核心决策

### 2.1 位置归属

多人模式的附近位置以房主为准。

- 房主配置自己的高德 Key 和安全配置。
- 房主负责定位或手动选点。
- 房主负责调用高德搜索和 fastText 分类。
- 成员不需要配置高德 Key，也不需要申请定位权限。
- 房主保存结果后，所有成员使用同一份数据。

不采用“每个成员分别搜索后合并”的方案，因为它会造成商家集合不同、结果不可复现、定位隐私泄露和高德配额难以控制。

### 2.2 数据归属

高德请求和分类过程属于房主客户端；已分类的结果快照属于房间，并在开始游戏时复制到 round。

服务端不代理高德请求，也不接收高德 Key、securityJsCode 或精确定位坐标。

### 2.3 游戏数据

多人周围菜品使用内置“大类菜品”作为聚合目标：

- 只生成能匹配内置大类的卡片。
- 无法可靠归类的商家不进入游戏。
- 同一大类只生成一张卡片。
- 卡片封面、名称、说明和标签来自内置菜单。
- 卡片的“代表食物”区域改为“附近门店”，显示该大类下聚合的真实门店名称。
- 卡片顺序由房主生成并冻结，客户端不得重新排序。

高德原始分类只作为 fastText 的输入，不作为多人游戏的数据集类型。

## 3. 用户流程

### 3.1 房主

~~~text
进入多人游戏
→ 创建房间
→ 房间页选择“周围菜品”
→ 进入周围菜品配置页
→ 定位或手动选择位置
→ 搜索附近餐厅
→ 按 rating 选择候选商家
→ fastText 转换为内置大类
→ 过滤无法归类的商家
→ 预览生成的菜品卡片
→ 保存到房间
→ 返回房间页
→ 开始多人游戏
~~~

配置页保存成功后，房间页显示已准备的类别数和门店数。房主在房间处于 waiting 状态时可以重新进入配置页并替换快照。

### 3.2 成员

~~~text
加入房间
→ 看到房主正在准备或已经准备周围菜品
→ 等待房主开始
→ 收到 round.started
→ 使用房主冻结的卡片进行游戏
→ 提交自己的选择
→ 查看多人结果
~~~

成员只看到准备状态和摘要，不进入高德配置页，不使用成员自己的位置。

### 3.3 状态

房间级附近菜品有三种展示状态：

- 未配置：没有有效快照。
- 配置中：房主正在配置，房间仍保持上一份有效快照。
- 已准备：存在通过校验的快照。

搜索、定位或分类失败时，房间保持上一份有效快照和原有数据集选择，不清空数据，不增加 revision。

## 4. 房间页面行为

### 4.1 房主

房主的数据集选择区域新增“周围菜品”。

点击后进入配置页。配置成功后自动将房间数据集设置为 nearby，并把附近快照保存到房间。

房间页展示：

~~~text
周围菜品
已准备 4 个菜品 · 20 家附近门店
重新配置
~~~

没有有效快照时，开始游戏按钮不可用，并提示房主先完成配置。

### 4.2 成员

成员端只读展示：

~~~text
周围菜品
等待房主准备
~~~

或：

~~~text
周围菜品
已准备 4 个菜品
等待房主开始
~~~

成员不能修改数据集、重新搜索或开始游戏。

### 4.3 切换和冻结

等待状态下：

- 房主可以切换回大类、小类或自定义菜品。
- 已保存的附近快照可以保留，以便之后切回 nearby。
- 房主可以重新搜索并替换附近快照。

开始 round 后：

- 附近快照复制到 round。
- 房间附近快照和 round 快照都不可修改。
- 房主不能重新搜索。
- 新成员不能加入当前对局。
- 任何客户端都不再调用高德 API。

## 5. 数据模型

### 5.1 数据集类型

房间数据集类型从：

~~~text
large | small | custom
~~~

扩展为：

~~~text
large | small | custom | nearby
~~~

### 5.2 NearbyCatalogSnapshot

房间和 round 使用同一份规范化快照结构。selectionHash 由服务端对规范化快照生成，客户端提交的输入不包含该字段：

~~~ts
type NearbyCatalogSnapshot = {
  version: 1;
  catalogVersion: string;
  catalogHash: string;
  classifierVersion: string;
  selectionHash: string;
  itemIds: string[];
  items: Array<{
    itemId: string;
    merchantNames: string[];
  }>;
  searchRadiusMeters: number;
  candidateCount: number;
  preparedAt: string;
};
~~~

其中 itemId 必须是当前内置大类菜单中的正式 ID，例如 cantonese、sichuan、hotpot 或 western。这样多人决策和结果计算可以继续使用已有的内置菜单 ID。

附近门店名称是覆盖在内置卡片上的动态展示字段，不改变内置菜品身份。

### 5.3 房间摘要

常规房间快照只返回：

~~~ts
type NearbyCatalogSummary = {
  selectionHash: string;
  catalogVersion: string;
  categoryCount: number;
  merchantCount: number;
  preparedAt: string;
};
~~~

不在 WebSocket 和常规房间状态中重复携带完整门店列表。

### 5.4 存储边界

房间或 round 中不保存：

- 高德 Key。
- securityJsCode。
- 精确经纬度。
- 完整高德原始响应。
- 高德图片地址。
- 成员自己的位置。

只保存已经过滤、去重和截断后的大类与门店名称。

## 6. 服务端接口

### 6.1 保存附近快照

新增：

~~~text
PUT /api/rooms/:roomId/nearby-catalog
~~~

请求包含：

~~~ts
type SaveNearbyCatalogRequest = {
  expectedRevision: number;
  catalog: Omit<NearbyCatalogSnapshot, 'selectionHash' | 'preparedAt'>;
};
~~~

服务端必须：

1. 验证操作者是房主。
2. 验证房间仍处于 waiting。
3. 验证 expectedRevision。
4. 验证 catalogVersion 和 catalogHash 对应当前内置菜单。
5. 验证 itemId 都是有效的大类 ID。
6. 验证 itemIds 无重复，且与 items 一一对应。
7. 验证至少有 3 个有效大类。
8. 验证门店名称长度、数量和快照总大小。
9. 规范化快照并由服务端计算 selectionHash 和 preparedAt。
10. 事务内保存附近快照并设置 selectedDataset=nearby。
11. revision 增加一次。
12. 发布 room.updated。

服务端不负责重新调用高德或重新运行分类器。分类器版本和选择哈希只用于追踪和一致性校验。

### 6.2 读取附近快照

建议新增：

~~~text
GET /api/rooms/:roomId/nearby-catalog
~~~

仅房间成员可以读取。普通房间快照仍然只返回摘要，客户端在本地 hash 缺失或发生变化时读取完整快照。

### 6.3 开始 round

现有开始 round 接口保持：

~~~text
POST /api/rooms/:roomId/rounds
~~~

请求仍只携带 expectedRoomRevision。服务端根据房间 selectedDataset 处理：

- large：锁定大类菜单版本。
- small：锁定小类菜单版本。
- custom：复制房间自定义快照。
- nearby：复制房间附近菜品快照。

nearby 数据不足、快照失效或菜单版本不一致时，拒绝开始，不改变房间状态。

### 6.4 Round 和结果

nearby round 的快照需要随 round 状态恢复给成员，至少包含：

- datasetType=nearby；
- catalogVersion 和 catalogHash；
- 有序 itemIds；
- 每个 itemId 对应的 merchantNames。

结果页也必须能够读取同一份快照，不能依赖房间当前状态或再次搜索。

## 7. revision 和实时同步

### 7.1 会增加 revision 的操作

- 房主切换数据集。
- 房主保存或替换附近快照。
- 成员加入或退出。
- 房主开始 round。
- 房间状态变化。
- 房主开放下一轮。

### 7.2 不会增加 revision 的操作

- 读取房间。
- 读取附近快照。
- 成员进入页面。
- 成员提交个人喜欢或不喜欢。
- WebSocket 心跳和重连。

### 7.3 room.updated

保存附近快照后发送摘要事件：

~~~json
{
  "type": "room.updated",
  "roomId": "room_xxx",
  "roomRevision": 10,
  "nearbyCatalog": {
    "selectionHash": "abc123",
    "categoryCount": 4,
    "merchantCount": 20
  }
}
~~~

成员收到事件后拉取最新房间状态，并在 hash 变化时读取完整快照。

事件不携带高德原始数据、坐标或高德 Key。

## 8. 客户端实现

### 8.1 Web

复用现有周围菜品搜索页，增加 multiplayer 场景：

~~~text
/room/:roomId/nearby?mode=multiplayer
~~~

单人场景继续保存本地 nearby round；多人场景改为调用 saveNearbyCatalog，成功后返回房间页。

房间页新增：

- nearby 数据集入口；
- 房主配置入口；
- 已准备摘要；
- 无快照时的禁用状态；
- 成员只读状态。

### 8.2 小程序

复用现有周围菜品页、定位页和高德适配器，增加：

~~~text
/pages/nearby/index?mode=multiplayer&roomId=xxx
~~~

多人场景下：

- 仍然由房主端使用本地高德配置；
- 仍然通过 wx.getLocation 或手动选点搜索；
- 不创建单人本地 nearby round；
- 保存服务端快照后返回房间页。

成员端不进入该页面，不发起高德请求。

### 8.3 游戏页

Web 和小程序继续复用现有多人游戏页、SwipeDeck 和选择发送队列。

当 round.datasetType=nearby 时：

- 使用内置大类卡片模板；
- 使用 round 快照中的 itemIds；
- 用 merchantNames 覆盖“附近门店”区域；
- 保持现有卡片高度、滑动布局、喜欢/不喜欢动画和进度同步；
- 决策仍然提交内置大类 itemId。

客户端不得根据自己的菜单顺序或重新分类结果生成卡片顺序。

### 8.4 结果页

结果页根据 round 快照将内置大类 ID 还原成：

~~~text
粤菜
附近门店：广东道至正家宴、茶餐厅
~~~

结果刷新、断线重连和重新进入时都使用冻结快照。

## 9. 错误和恢复

### 9.1 房主配置失败

定位失败、高德请求失败、分类器加载失败或没有足够有效大类时：

- 不保存新快照；
- 不修改 selectedDataset；
- 不增加 revision；
- 保留上一版有效附近数据；
- 给房主重试和手动选点入口。

### 9.2 revision 冲突

客户端收到 ROOM_REVISION_CONFLICT 时：

1. 拉取最新房间快照。
2. 不自动覆盖房间数据。
3. 如果仍由当前用户担任房主，提示重新确认后保存。

只有无风险的状态刷新可以自动重试，附近结果替换不能在版本冲突后静默覆盖。

### 9.3 成员恢复

成员加入或断线恢复时：

- 读取房间摘要；
- 根据 selectionHash 读取完整附近快照；
- 开始游戏后直接读取 round 快照；
- 不需要高德 Key；
- 不需要重新定位；
- 不需要重新分类。

### 9.4 菜单版本失效

如果房间附近快照引用的菜单版本或 itemId 已不存在：

- 标记附近快照不可开始；
- 房间页提示房主重新搜索；
- 不影响已经开始的旧 round；
- 不删除旧 round 快照。

## 10. 功能边界

### 本次包含

- 房主位置搜索。
- 用户自备高德 Key。
- Web 和小程序房间入口。
- fastText 分类和内置大类聚合。
- 房间级附近快照。
- 多人实时准备状态。
- round 冻结。
- 现有多人卡片和结果复用。
- 刷新、断线和重连恢复。

### 本次不包含

- 成员分别搜索并合并。
- 服务端代理高德。
- 成员上传高德 Key。
- 游戏中实时搜索。
- 原始 POI 同步。
- 高德图片作为封面。
- 房主转移。
- 成员修改房主结果。
- 附近商家价格、营业状态、导航或下单。
- 运行时编辑内置菜品。

## 11. 测试计划

### 合约和服务端

- nearby 数据集和快照 schema。
- 无效大类、重复大类、少于 3 类。
- 非房主、非 waiting 状态和 revision 冲突。
- 保存失败保留旧快照。
- 开始 round 正确复制快照。
- 普通房间事件不泄露 Key、坐标和原始 POI。
- round 和 result 可以恢复门店名称。

### Web 和小程序

- 房主可以配置并保存。
- 成员只读看到准备状态。
- 成员不调用高德。
- 房主重新搜索后成员能收到更新。
- 游戏开始后无法修改。
- 两端卡片 ID、顺序、封面和门店名称一致。
- 没有高德配置的成员可以正常游戏。

### 双端联机

至少验证以下组合：

- Web 房主 + Web 成员。
- Web 房主 + 小程序成员。
- 小程序房主 + Web 成员。
- 小程序房主 + 小程序成员。

每种组合都验证加入、准备、开始、左右滑、完成、刷新和断线重连。

## 12. 分阶段实施

1. 更新 contracts、数据库和服务端附近快照接口。
2. 抽取共享快照规范化、哈希和卡片还原模块。
3. 接入 Web 房间页、配置页、游戏页和结果页。
4. 接入小程序房间页、配置页、游戏页和结果页。
5. 完成双端联机、异常恢复和菜单版本测试。
6. 更新实现文档、运行验证并提交代码。

实现第一阶段不应改变单人周围菜品流程，也不应重写已经验证过的滑卡组件。

## 13. 验收标准

1. 房主可以使用自己的位置搜索附近餐厅。
2. 成员不需要高德 Key 或定位权限。
3. 房主和成员使用完全相同的冻结数据。
4. 只有房主可以在等待状态重新搜索。
5. 开始游戏后附近数据不可变化。
6. 游戏卡片继续使用现有多人布局。
7. 卡片封面来自内置大类菜单。
8. 卡片显示真实门店名称，并且超长时截断。
9. 无法匹配内置大类的商家不进入游戏。
10. Web 和小程序可以混合联机。
11. 刷新和断线恢复不会重新搜索或分类。
12. 高德请求失败不会破坏上一版有效结果。
